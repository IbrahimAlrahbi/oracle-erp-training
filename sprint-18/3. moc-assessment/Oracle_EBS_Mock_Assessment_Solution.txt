QUESTION 3 - MD50 FUNCTIONAL DESIGN
============================================================


1. BUSINESS REQUIREMENT

   An employee submits a leave request, the request is sent
   to the employee's manager, and the manager approves or rejects it.



2. CURRENT PROCESS / AS-IS

3. PROPOSED PROCESS / TO-BE

   1. Employee submits a leave request.
   2. The request is routed to the confirmed manager.
   3. The manager receives and reviews the notification.
   4. The manager selects Approve or Reject.
   5. The request records the corresponding outcome.

4. FUNCTIONAL REQUIREMENTS

   - Allow an employee to submit a leave request.
   - Route the request to a manager.
   - Generate a notification for the approver.
   - Allow the approver to choose Approve or Reject.
   - Follow the corresponding workflow branch and finish correctly.


5. BUSINESS RULES

   - The decision path is Employee -> Manager -> Approved/Rejected.
   - Approve produces Approved; Reject produces Rejected.

6. WORKFLOW / INTEGRATION REQUIREMENTS

   Use an Oracle Workflow Item Type, Process, activities, notification,

7. ASSUMPTIONS AND DEPENDENCIES

   - Valid employee and manager EBS users are available.
   - The correct manager is confirmed before execution.
   - Workflow Builder, database connectivity and the demonstrated
        Workflow Administrator responsibility are available.




QUESTION 4 - MD70 TECHNICAL DESIGN 
============================================================


1. TECHNICAL SOLUTION

   Proposed object names:
   Item Type: IBRLWF
   Display Name: IBRAHIM Leave Approval
   Process: IBRA_LEAVE_PROCESS
   Message: IBRA_LEAVE_MSG
   Notification: IBRA_LEAVE_NOTIFY


2. TECHNICAL ARCHITECTURE / FLOW 

   Logical design:
   Employee submission -> request data -> workflow instance
      -> manager notification -> manager response
         -> Approved outcome OR Rejected outcome -> End

   Proposed data flow:
   1. Submission supplies request identity, employee, manager and dates.
   2. The request identity is associated with its workflow instance.
   3. Manager response is associated with that same request.
   4. The final decision is retained and visible for verification.

   S9/S10 cover the basic workflow and manual test launch only.
   The actual submission-to-workflow interface is not specified.

3. DATABASE OBJECTS 

   Proposed fields and purpose:
   REQUEST_ID       Unique request identifier
   EMPLOYEE_USER    Submitting employee account
   MANAGER_USER     Assigned manager account
   START_DATE       Leave start date
   END_DATE         Leave end date
   LEAVE_REASON     Request explanation
   STATUS           Submitted / Approved / Rejected (proposed values)
   WORKFLOW_ITEM_KEY Reference to the workflow instance
   DECISION_DATE    Time the final decision is recorded


4. PL/SQL / API / WORKFLOW COMPONENTS 

   Workflow components:
   IBRLWF, IBRA_LEAVE_PROCESS, IBRA_LEAVE_MSG, IBRA_LEAVE_NOTIFY.
   Required logical activities:
   Start, Submit Leave, Manager Approval, Approved, Rejected, End.


5. PROGRAM / FORM / CONCURRENT PROGRAM DETAILS

   Supplied lab entry point:
   Workflow Administrator Web Application
      -> Administrator Workflow
         -> Developer Studio
            -> <Run>


6. ERROR HANDLING & LOGGING 

   - Missing required request data:
     Identify the missing value; do not submit an incomplete request.
   - End date before start date:
     Reject the input and request corrected dates.
   - Manager unavailable/unresolved:
     Record the routing problem; do not mark the request approved.
   - Notification/processing failure:
     Retain request and workflow identifiers for investigation.
   - Invalid or duplicate final decision:
     Preserve one final outcome and record the rejected operation.

7. TESTING CONSIDERATIONS

   - Submit a request -> workflow instance starts.
   - Notification is generated and reaches the assigned manager.
   - Approve -> Approved path -> correct end activity.
   - Reject on a separate request -> Rejected path -> correct end.
